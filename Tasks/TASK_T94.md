# T94 — Drag-and-drop reorder for the category list
- **Goal:** Category rows on the management page reorder via an ≡ handle on the right, like item rows, persisting the new order.
- **Inputs:** `category-list.tsx` (rows without handles), item-row DnD pattern (`useSortable`, TouchSensor delay/tolerance, handle-only drags), item reorder backend (`reorderItems` + `POST /lists/:id/items/reorder` + `reorderRequestSchema`) as the template; no category reorder endpoint exists today.
- **Outputs:** Shared zod schema for category reorder (`orderedIds`, no status field); `reorderCategories` service (same-list validation, `sortOrder` rewrite in one transaction); `POST /lists/:id/categories/reorder` (EDITOR+); `docs/API.md` updated; category rows become sortable with ≡ handles (VIEWER sees none); `useReorderCategories` mutation with optimistic update + rollback and cache invalidation (categories, items grouping, combobox order).
- **Test cases:** 1. Setup: Dairy above Bakery; Action: drag Bakery above Dairy via ≡; Expected: order flips on screen and a refetch returns the new `sortOrder`. 2. Setup: EDITOR member; Action: POST reorder with a foreign-list id, an unknown id, and as a non-member; Expected: rejection (same guards as item reorder) and order unchanged. 3. Setup: signed in as VIEWER; Action: open the page; Expected: no handles, no reorder calls. 4. Setup: reorder mutation fails; Action: drag a row; Expected: previous order restored and an error shown. 5. Setup: reordered categories; Action: open the main screen and the item-edit category picker; Expected: grouping and picker follow the new order. 6. Setup: touch device; Action: tap a row vs drag from ≡; Expected: tap still opens the items view, only handle-drags reorder.
- **Definition of Done:** Test cases 1–6 pinned by specs (API contract tests mirroring item reorder + component tests for handles, optimistic rollback, and tap-vs-drag); full gate green.
- **Dependencies:** T93.
